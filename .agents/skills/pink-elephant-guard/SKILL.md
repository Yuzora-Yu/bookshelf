# Pink Elephant Guard / ピンクの象ガード

## 原則

ユーザーと作り手の間で扱う制作情報と、成果物の受け手へ届ける情報を分ける。

修正指示は判断と実装に反映する。指示そのもの、指示された経緯、理解したという宣言、従ったという弁明を、本文やコードなどへ持ち込まない。制作情報の混入はゼロを要件とする。

適用範囲は成果物全般。修正のある場面では、却下案が否定や言い換えを通じて再登場していないかも調べる。修正履歴のない新規制作でも、依頼文と完成物の境界を守る。

## 情報を置く場所

制作情報：依頼、訂正、却下理由、作業の相談、指示への返答、検査の手順。チャットや明示的に用意した制作資料で扱う。

成果物の内容：読み手が知るべき事実、作品の出来事、製品の機能、利用方法、保守に必要な設計理由。成果物の目的に沿って書く。

掲載の可否は、ファイル形式でなく受け手と用途で判断する。指示書は担当者への依頼を、講評は問題箇所と根拠を、変更記録は依頼された変更履歴を扱う。それらに書ける内容を、小説本文や製品のコードへ流用しない。

ユーザーが履歴そのものを成果物として求めた場合は、指定された資料に記録する。作り手の判断で「説明した方が親切」という例外を設けない。必要な法的表示・安全情報・技術上の注意は、成果物の内容として保持する。

## 制作手順

1. **受け手と用途を定める。** 納品物の各部分を誰が何のために読むか確認する。制作資料と公開・配布用の内容を分ける。
2. **要件へ変換する。** 会話から現在有効な事実、期待する結果、制約を取り出す。訂正に返事をする文章を、そのまま完成文に使わない。
3. **目的から作る。** 読者の理解、人物の行動、コードの動作として要件を実現する。元案を中心に書かれた箇所は、段落・場面・実装の役割から組み直す。
4. **出力全体を確認する。** 下記の観点で、制作情報と却下案の混入を調べる。
5. **該当箇所を再構成する。** 混入の原因を除き、完成物として読み直す。修正の単位は問題の及ぶ範囲に合わせる。確認済みで有効な部分は保つ。

要件に必要な禁止や否定は明記する。肯定形への言い換えで意味や強さを落とさない。

## 確認する箇所

- **直接の混入**：依頼文の転記、ユーザーへの返事、訂正された事実や却下案の再掲。
- **意味の混入**：否定、比較、言い換え、弁明として制作会話が残っている。
- **構成への混入**：見出し、冒頭、結びが依頼への応答や変更理由を主題にしている。
- **周辺への混入**：コードコメント、識別子、テスト名、ログ、エラー文、UI、注釈、代替テキスト、メタデータに会話の痕跡がある。
- **視覚・音声への混入**：削除対象の形や断片、旧案の字幕・台詞・音が残っている。

語句の一致だけで判定しない。その記述が制作会話を知らない受け手にも、用途に沿った意味を持つか確かめる。実際に見聞きしていない画像・動画・音声を、検査済みと報告しない。

## 媒体ごとの扱い

### 本文・小説

作者への注文は、人物、出来事、文体の選択へ反映する。地の文や台詞で、注文に従ったことを説明しない。

人物の拒絶、嘘、未練、誤解、伏線は作品内部の内容である。制作履歴との区別をつけて扱う。台詞や動作の後の説明は、場面に必要な新しい意味を加えるか確認する。

### コード・UI

求められた挙動を実装し、コメントは現在の処理、前提、保守に必要な理由を説明する。修正依頼の文言やユーザーとの応酬をコメント、ログ、表示文言へ書き込まない。

設計上の制約や互換性上の理由は、保守者が実装を理解するための情報として記載できる。会話の経緯を技術的理由の代わりに使わない。

### 指示書・講評・報告

受け手に必要な依頼、根拠、結果を書く。担当者向けの指示書には仕事と参照先を、講評には本文の引用と評価を示す。これらは資料の目的に属する。

ユーザーと作り手の間でしか意味を持たない訂正への応答や、指示を理解したという説明は、資料へ付け足さない。ユーザーへの作業報告はチャットで簡潔に行う。

### 画像・動画

確定した被写体、配置、動き、音を指定する。却下した要素を中心とする構図や脚本を残さない。生成指示と、実際に画像・映像・音声へ載せる内容を分ける。

## 完了条件

制作指示への応答や、その経緯の混入がないこと。必要な要件と根拠が保たれ、受け手が成果物だけで理解・利用できること。

確認結果の説明は、求められた報告先へ出す。完成稿だけを求められた場合は、完成稿だけを返す。

判断例と確認範囲は [references/specification.md](references/specification.md) を参照する。
