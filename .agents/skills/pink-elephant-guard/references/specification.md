# 制作情報と成果物を分けるための判断例

この資料は、スキルを使う担当者向けの説明である。ここにある指示文の引用や対比例を、小説本文・コード・UIへ転記しない。

## 境界の判断

判断するのは表現の肯定・否定ではなく、情報の用途である。

|情報|置く場所・反映方法|
|---|---|
|ユーザーが台詞を分かりやすくするよう注文した|制作中の依頼として理解し、本文の話者と動作を整える|
|登場人物が帰宅を拒む|作品内の意思として、台詞や行動に書ける|
|担当者に講評を読んでほしい|担当者向けの指示書に、読む資料と作業を記載する|
|指示書の作成者が、相手の既読状態を勘違いして訂正された|制作中の理解を修正し、指示書では必要な資料を案内する|
|不具合の修正を依頼された|挙動を直す。コードでは現在の処理と必要な設計理由を説明する|
|変更履歴の提出を依頼された|指定された変更記録に、対象の変更を記載する|

## 指示書の例

依頼の背景として、担当者が講評を未読だと分かっている。

担当者に渡す文：

> 二〜四作目は、各フォルダの講評を全文読んでから、本文の点検と修正に進んでください。

未読という情報は作業の順序に反映されている。作成中にその情報を訂正された経緯は、この依頼を理解するために必要ない。

## コードコメントの例

制作会話の混入：

```python
# ユーザーに指摘されたので、空欄で落ちないようにした。
```

保守に必要な理由を記載する例：

```python
# 空欄は未設定として扱う。
```

後者が実際の仕様と一致する場合に記載する。自明な処理ならコメント自体を省ける。テスト名も、修正を頼んだ人ではなく検証する挙動を示す。

## 小説の例

「人物の声を分けて」という依頼を受けたときは、人物ごとの欲求や相手との関係から発言を組み立てる。「彼は自分らしい言葉で話した」と地の文へ書けば依頼を実現したことにはならない。

人物が「帰りたくない」と言うことや、探偵が仮説を否定することは、作品の内容である。制作情報の混入を禁じる規則は、これらを禁止しない。

## 講評・記録の例

講評の本文引用と修正前後の比較は、評価を理解するための根拠になる。必要な批判を残す。

変更履歴を明示的に求められた場合は、その記録の受け手に必要な履歴を記す。記録用に許された内容を、作品や製品へも載せてよいとは扱わない。

## 強い制約の保持

「二〜四作目のチャット報告はネタバレなし」は報告の要件である。指示書に明記し、実際の報告で守る。報告のたびに秘密の中身を挙げて「これは書きません」と説明すると、要件に反する。

## 確認範囲

この版では、指示書、小説、コード、講評、履歴資料の区別を上記の例で確認する。画像・動画・音声は、実物を確認した範囲だけを検査済みとする。

形式検証とリンク確認は、個々の生成結果の品質保証とは別である。以前の版の試験結果を、この版の実測結果として引き継がない。独立した担当者による動作試験を実施した場合は、その条件と実際の結果を別途記録する。
